`noodle` manages the runtime, models and runners. Docker commands go to the real `docker` CLI with `--context noodle`. Run `noodle help` for the groups, `noodle <group> help` for one group, or `noodle help --json` for the whole table as JSON. A group with no subcommand prints its help and exits 0, the same as `noodle <group> help`. `noodle names`, `proxy` and `link` run their own bare form instead. Each command here is generated from that table.

## Notes on commands

- **setup**: sets up clients, the Docker context and the LaunchAgent. It selects the Noodle context when no other engine is running; `--use` forces it and `--no-use` never does. `--tools` prefetches plugins.
- **uninstall**: removes Noodle-owned setup items. Data is kept unless you pass `--delete-data`.
- **status**: `noodle status --startup` reports Docker API, VM and guest readiness. See [Status for scripts](#status).
- **tools**: manages the pinned Docker clients and BuildKit.
- **model**: `location [<folder>]` or `location --reset` sets where models install. `keep-alive [<duration>]` or `keep-alive --reset` saves how long a model stays loaded. `key [--rotate]` prints or replaces the API key. `network [on]`, `network off` or `network --json` lets other devices use your models. GGUF `run` and `serve` accept `--keep-alive`; `serve` also accepts `--port` and `--workloads`.
- **proxy**: reads or changes the registry proxy and the optional environment for new containers.
- **import**: copies from a Docker context, a Unix socket or a running `podman` machine. Stop volume writers before copying.
- **share**: manages approved absolute folders for file binds. `remove --restart` ends access for the privileged VM and the Kubernetes node now, instead of at their next restart.
- **machine**: see [Machines and raw VMs](/docs/containers/machines/).
- **pod**: add members with `docker run`, see [noodle pod](/docs/containers/#pod).
- **runners**: see [Runners](/docs/runners/). `doctor` checks that this Mac is ready, see [Check this Mac](/docs/runners/doctor/). `clean` frees disk tier by tier and never asks; it exits 1 if a deletion failed.
- **image**, **container**: `noodle image layers` and `noodle container edit|ports` are the only subcommands. Use `docker --context noodle image` and `docker --context noodle container` for the rest.
- **logs**: `--raw` disables secret redaction. For a container's logs use `docker --context noodle logs NAME`.
- **scan**: `--history [IMAGE]` shows scan history and `--clear-cache` clears it.

Set VM CPUs and memory in the app, or in `~/.noodle/vm.json` with `cpus` and `memory_mib`. `NOODLE_HOME` changes that directory; `NOODLE_CPUS` and `NOODLE_MEMORY_MIB` override the file. Set `"host_loopback": false` in the same file to disable the relay at the next daemon start.

## Docker commands

Noodle does not wrap `docker`. An unknown `noodle` command points you to `docker --context noodle`. If you selected Noodle as the default context with `noodle setup --use`, plain `docker` commands also target it:

```sh
docker --context noodle run -d -p 8080:80 nginx
docker run -d -p 8080:80 nginx
```

The socket path is printed by `noodle status`.

<span id="logs"></span>

## Container logs and the Mac

Log rotation follows Docker. `--log-opt max-size=10k --log-opt max-file=3` keeps at most three files per container, `docker logs` reads them in order, `--tail` and `--follow` work across a rotation, and bad values are refused with exit 125. Without the options nothing is rotated. The `local` driver takes the same options.

Inside an ordinary container on a non-internal network, `host.docker.internal` and `--add-host name:host-gateway` reach Mac loopback TCP services through a relay by default. Noodle's own loopback listeners are protected. Internal networks, UDP and privileged containers in the workload VM do not use the relay. Setting `host_loopback` to `false` restores NAT-only reach.

## Exit codes

Every group uses the same codes. Usage and unknown-command text goes to stderr.

{/* cli-exit-codes:start */}
| Code | Meaning |
| --- | --- |
| `0` | success |
| `1` | the operation failed |
| `2` | usage error, a confirmation needed with no terminal and no --yes, or (scan --fail-on) a finding at or above the threshold |
| `3` | the engine is not running or not reachable |
{/* cli-exit-codes:end */}

A declined confirmation, a timeout and a failed operation all exit 1. A command that needs a confirmation but has no terminal exits 2 and names the flag: pass `--yes` (`-y`, `-f` and `--force` also work). `noodle kubernetes status` and `noodle status` exit 3 when the engine or cluster is not running. The `--json` form of `kubernetes status` always exits 0 and reports the state in the document. `noodle scan --fail-on` exits 2 when a finding meets the threshold.

A few exit codes come from outside Noodle. A command that runs `docker`, `kubectl` or `noodle-machine` exits 127 when that program is missing and 126 when it cannot be run. `noodle machine shell` exits 255 when it loses the connection to the machine. `noodle names trust` and `untrust` exit 1 when the macOS `security` tool fails.

<span id="json"></span>

## JSON output

Without `--json`, output is for a person, on the same streams as always. With `--json`, stdout is one JSON document and progress, status chatter and failure messages go to stderr. These commands print a document with `schemaVersion: 1`: `version`, `status`, `status --startup`, `doctor`, `tools status`, `update check`, `update status`, `machine status NAME`, `kubernetes start` and `status`, `runners list`, `status`, `repos`, `check`, `cache`, `doctor`, `clean` and `toolchains`, `diagnostics` and `import`. `machine list`, `model list`, `status`, `endpoint`, `catalog` and `network`, `builds list`, `container ports`, `image layers`, `scan`, `proxy`, `names`, `link` and `pod` take `--json` too but keep the shape they had before, which may be a bare array or a shape the app reads, so they have no `schemaVersion`. An error with `--json` is still a non-zero exit with a message on stderr; there is no JSON error envelope.

`noodle model run` reads prompts from piped standard input and answers on stdout, so it works in a pipe; it never prompts for a confirmation.

<span id="status"></span>

## Status for scripts

`noodle status --json` prints one JSON object with `schemaVersion: 1` and never starts the daemon or the VM.

- `daemon.reachable` is true when the socket answers `/_ping`. It does not say whether the VM is running.
- `paths.data`, `paths.socket` and `paths.launchAgent` are the resolved paths.
- `tools.docker.available` and `tools.docker.path` report whether a Docker CLI was found.

It exits 0 when the socket answers, 3 when it does not, and 1 on an encoding error. An unreachable daemon is still a valid snapshot.
