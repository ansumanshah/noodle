# Host <-> guest protocol (v1)

Transport: virtio-vsock, guest listens. All integers big-endian. JSON is UTF-8 and compact.

Ports: 1030 (SSH agent relay), 1035 (Docker API relay, main VM only), 1031 (ready) and 1034 (Mac loopback relay, main VM only) are host listeners the guest dials; 1032 (control) and 1033 (streams) are guest listeners the host dials. `NoodleWire` in `Sources/NoodleCore/Frames.swift`, `HostLoopback.vsockPort` in `Sources/NoodleCore/HostLoopback.swift` and the port constants in `guest/agent/src/main.zig`, `sshagent.zig` (ports 1030 and 1035) and `hostlo.zig` must match this list.

## Port 1034: Mac loopback relay
Guest-initiated, one connection per relayed TCP connection, main VM only. The host listens from daemon start unless `host_loopback` is `false` in `vm.json`; the privileged containers VM never gets the listener.

The guest sends an 8-byte header, then raw bytes both ways:

| bytes | field |
|---|---|
| 0 | `u8 version`, 1 |
| 1 | `u8 family`, 4 (IPv4; nothing else is defined) |
| 2-3 | `u16 port`, the TCP destination port the container dialled, nonzero |
| 4-7 | the IPv4 destination the container dialled: the VM's DHCP router, the Mac's end of the NAT link |

The host sends nothing before relaying. Any other version or family, a zero port, or a connection beyond 64 open relays is closed without a byte. The host then connects, in order, to `127.0.0.1:port`, `[::1]:port`, and the header address, the last only when that address belongs to a Mac `bridge100`-or-above interface. A port Noodle itself listens on at Mac loopback skips both loopback targets, so it is reachable only as it was before the relay, through the NAT address. Those ports are claimed in one per-user directory, `~/Library/Application Support/Noodle/loopback-claims/<port>/<pid>`, before their listener listens: local-name ports, the Finder server and public-link fronts by the daemon that owns them, and a model server by its own process just before it execs, whatever `NOODLE_HOME` started it. A claim whose process is gone is ignored and removed. 11345 and the port in this home's `models/session.json` always count. After a loopback connect succeeds the host checks the claims again and, if the port was claimed meanwhile, drops that connection and tries only the NAT address. When no target accepts, the host closes the connection and the container sees a reset after connect. When the main VM stops, the host closes both sides of every open relay.

Guest side: the `host_loopback` control op (below) opens a TCP listener on `0.0.0.0:61034`. Once the lease names the router, the agent first installs an input guard in table `noodle-hostlo` (`tcp dport 61034 ct status & dnat == 0 drop`), so only connections a redirect rewrote reach the listener, whatever address a container dials. Then it installs nftables `redirect` rules that send TCP to the router address, except port 53, to the listener. Without the guard it installs no redirect and serves nothing. Only non-internal IPv4 networks get the rule, in their own `noodle-<bridge>` table; `noodle-hostlo` also holds the rules for the VM's own traffic (`--network host`, BuildKit) and the BuildKit bridge. On accept the agent reads `SO_ORIGINAL_DST` and closes the connection unless the original address is the router. It accepts at most 8 connections per event-loop turn and forks a child per connection, at most 64 at once. The child keeps only the accepted socket (`close_range`), dials vsock 1034, writes the header and relays.

## Port 1032: control
One persistent connection from the host. Frames: `u32 length` + JSON object. A length above 16 MiB (`NoodleWire.maxControlFrame`, `max_frame` in the agent) is rejected; bulk data belongs on port 1033.

Request: `{"id":N,"op":"<name>", ...args}`
Response: `{"id":N,"ok":true, ...result}` or `{"id":N,"ok":false,"error":"text","errno":N}`
Event (no id): `{"event":"exit","container":"<id>","code":N}`, `{"event":"oom","container":"<id>"}`,
`{"event":"exec_exit","exec":"<id>","code":N}`, `{"event":"dns_query","id":N,"query":"<base64 DNS message>"}`

The agent must answer `ping` even while a layer is unpacking: long work runs in forked children or on stream connections, never in the main poll loop.

## Port 1033: streams
One connection per stream. First frame is a control-style JSON frame (`u32 length` + JSON), then the agent answers one JSON frame `{"ok":true}` or `{"ok":false,"error":"..."}`, then the stream body below.

Multiplexed body frames: `u8 kind`, `u32 length`, bytes.
kind: 0 stdin (host->guest), 1 stdout, 2 stderr, 3 exit (`i32` code, guest->host, last frame), 4 stdin EOF (host->guest, length 0), 5 resize (`u16 rows`, `u16 cols`, host->guest).

## On-demand Finder reads on port 1033

`finder_read` starts no persistent worker. Its stream child opens a container root (the running container's namespace, otherwise its merged rootfs) or a named volume root. Every path component is resolved with `openat2` using `RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_SYMLINKS`. Reject dot components, NUL, backslash, symlinks and non-file/non-directory objects. Roots themselves are opened without following caller-controlled symlinks. A stopped container is registered by the host but never started. For a stopped container path inside a volume mount, select that volume root using its validated spec and confine the remaining path there.

After normal acknowledgement, send one control-style JSON frame `{"kind":"file"|"directory","size":N,"mtime":unixSeconds}`. The metadata describes the opened descriptor. Then wait for a control-style host selection frame `{"action":"stat"|"list"|"read","offset":N,"count":N}` (maximum 1024 bytes). This lets the host select a Range against the same opened inode. `stat` closes without file data. `read` requires a regular file and `0 <= offset <= size`, `0 <= count <= size-offset`; return exactly `count` raw bytes then close, aborting on premature EOF. `list` requires a directory and returns control-style JSON frames `{"name":"basename","kind":"file"|"directory"|"symlink"|"other","size":N,"mtime":unixSeconds}` for direct children, then `{"end":true}`. Skip vanished entries; enumeration failures end with `{"error":"text","errno":N}`. There is no recursive walk or sorted name accumulation. Directory records are bounded to 4096 bytes and are sent one at a time with backpressure. Errors after acknowledgement use an error record only in directory mode; truncated metadata or file bodies are failures, never success.

The host bounds concurrent connections and requests. Closing the stream cancels a blocked child via EOF or a failed write. The host selects the existing container runtime. Volume records currently have no persistent VM placement, so an explicit standalone volume request probes the main disk and the workload disk if it already exists; this can wake both VMs. A volume name existing on both disks is ambiguous and must fail rather than silently choose or merge data. A host-created volume with no guest directory has an empty synthetic root until first use. Namespace listings, listener setup and status do not access guest storage. No daemon polling or guest timer is added.

## Container `spec`
```json
{"layers":["sha256:top","...","sha256:base"],"argv":[],"env":[],"cwd":"/","user":"0:0","tty":false,"stdin":false,
 "hostname":"","domainname":"","read_only":false,"privileged":false,"cap_add":[],"cap_drop":[],"seccomp":"default",
 "no_new_privs":false,"init":false,"ulimits":[{"name":"nofile","soft":1234,"hard":1234}],"sysctls":{"net.core.somaxconn":"1234"},"memory":0,"memory_swap":0,"memory_reservation":0,"cpus":0.0,"cpu_quota":0,"cpu_period":0,"cpu_shares":0,"pids_limit":0,"shm_size":67108864,"log_max_size":0,"log_max_file":1,
 "network_mode":"bridge","network":{"name":"bridge","ip":"172.18.0.2","gateway":"172.18.0.1","prefix":16,"mac":"","ip6":"fd6e:6f6f:646c:1::2","prefix6":64,"gateway6":"fd6e:6f6f:646c:1::1"},
 "dns":["172.18.0.1"],"dns_search":[],"dns_options":[],"hosts":["127.0.0.1 localhost"],
 "mounts":[{"kind":"bind|volume|tmpfs|agent","source":"","target":"","read_only":false,"no_copy":false,"tmpfs_size":0}]}
```
`ip6`, `prefix6` and `gateway6` are optional. On an IPv6-only network `ip` and `gateway` are empty and `prefix` is 0.

Ulimits are applied before dropping privileges; -1 means unlimited. Only `net.core.somaxconn` is currently accepted as a namespaced sysctl, and it is rejected when sharing a network namespace. When `init` is true, the guest bind mounts the bundled Tini binary read-only as `/dev/docker-init` and executes it as PID 1 with the container command; absent `init` means false. `cpu_quota` (microseconds per `cpu_period`, default 100000) takes precedence over `cpus` and is written to `cpu.max` as given. `memory_swap` is Docker's memory plus swap total: with `memory` set and `memory_swap >= memory`, `memory.swap.max` is `memory_swap - memory`; 0 or -1 leaves it unlimited. `memory_reservation` is written to `memory.low`. Cgroup limit and mount failures are returned to the caller.

`log_max_size` (bytes, optional, 0 or absent = never rotate) and `log_max_file` (optional, default 1) bound the container log; see "Log rotation".

`agent` mounts bind the guest SSH agent socket at `target` (the `source` field is informational: the host writes `/run/host-services/ssh-auth.sock`, the guest always uses its own socket path). They need a prior `ssh_agent` call and are not shared through virtiofs. `no_copy` is optional and defaults to false; for volume mounts it suppresses copying the image directory into an empty volume.
`docker` mounts work the same for the Docker API socket (`/run/noodle/docker.sock`, needs a prior `docker_api`). The host writes one when a bind source is Noodle's own `docker.sock` or `/var/run/docker.sock`; it hands the container full control of the engine, so it exists only on that explicit bind. `:ro` does not restrict it: the mount flag protects the socket file, not the API behind it.
`network_mode`: `bridge` (uses `network`), `host`, `none`, or `container:<id>`.
`create` may refresh a stopped container's spec while preserving its writable layer and log. Its image layers, tty, and stdin configuration must match; refreshing a running container fails.
The release host registers only explicitly requested host directories in virtiofs before guest `create`. Directory bind `source` is `/mnt/host/<share-key>`. A regular-file bind is `/mnt/host/<share-key>/<basename>`; the host shares that file's parent directory only after an explicit approval covering it, so the guest can access siblings in that approved directory. The share key is `k` + 24 hex of SHA-256 of the shared folder path + `r` (read-only) or `w`, so containers binding the same folder share guest inodes and keep warm caches between runs. The guest accepts only that shape and, for a file, one safe basename. Shares preserve the requested read-only mode and are revoked when the container stops or is removed. No host directories are shared by default.

## Guest boot
Kernel cmdline `console=hvc0 rdinit=/init quiet`. `/init` is the agent, in an initramfs.

The privileged containers VM (privileged and unconfined containers) boots the same kernel and agent with `noodle.role=workload` added. In that role the agent mounts the `host` virtiofs device only when the VM has one (the host adds it when Kubernetes shared folders are on), attaches the device policy (`devcg.zig`, a cgroup-device eBPF program on `/sys/fs/cgroup/noodle`) and refuses `privileged` containers if that fails; it rejects `bind` mounts unless that mount succeeded, accepts `privileged`/`seccomp=unconfined` specs and `exec` with `privileged`, and installs no seccomp filter for them. In the main VM those specs and `exec` flag are rejected.
1. Mount proc, sysfs, devtmpfs, devpts, tmpfs /run, cgroup2 at /sys/fs/cgroup; enable controllers cpu, memory, pids, io.
2. Mount `/dev/vda` (journaled ext4, formatted by the host) at `/var/lib/noodle`. A missing or failed disk mount stops guest startup; it never falls back to temporary storage.
3. Mount virtiofs tag `host` at `/mnt/host`. Mount virtiofs tag `rosetta` at `/mnt/rosetta` when present and register `rosetta` in binfmt_misc for x86-64 ELF (flags `CF`).
4. Bring up `eth0` with built-in DHCP client (the NAT device), then `lo`; ip_forward=1; nftables masquerade for container subnets.
5. Listen on vsock 1032 and 1033, then connect to the host on vsock 1031 and close. That connection carries no data and only says the listeners exist, so the host does not poll during a boot.
Layout: `/var/lib/noodle/{layers/verified-v1/<hex>/published/{root,diff-id},containers/<id>/{upper,work,merged,log},volumes/<name>}`.

## Log format
`containers/<id>/log`: frames `u8 stream` (1|2), `i64 unix_nanos`, `u32 length`, bytes.

### Log rotation
The host validates the Docker `json-file` and `local` options (`max-size`, `max-file`) and sends the result as `log_max_size` and `log_max_file` in the `create` spec. Without them the log is never rotated. Rotation happens on the write path, inside the same call that appends a frame, with no timer: when the current file is not empty and the next frame would take it past `log_max_size`, the agent shifts `log.(n-2)` to `log.(n-1)` and so on up from `log`, so `log` stays the current file, `log.1` is the newest rotated file and `log.<log_max_file-1>` the oldest. The oldest file is replaced. With `log_max_file` 1 the full file is deleted and a new `log` starts. A frame is never split across files, so a file can stay under the limit but never passes it except for one frame larger than the limit in an empty file. A refresh `create` on a stopped container updates both values.

`logs` and `attach` read the rotated files oldest first, then `log`. `tail` counts lines across all files. A follower keeps its open file, drains it after it has been renamed, then moves to the next newer file (found by inode), so a rotation loses no lines unless more than `log_max_file` rotations happen between two reads.

## Clarifications fixed by the guest agent (Zig, `guest/agent`)
These pin down points the tables above leave open. Host code should rely on them.
- **Layer keys.** The agent hashes all blob bytes against `digest` and all decompressed tar bytes against `diff_id`. The compressed stream must end exactly at its declared size. Only then does it atomically publish a bundle containing the overlay lowerdir and a sibling verification record beneath `layers/verified-v1/<hex>`. Older directories have no verification record and require unpacking again. OCI whiteouts remain inside the lowerdir.
- **`layer_has`** returns `present` for matching verified blob/diff-ID pairs. A digest paired with a different diff ID is a miss. The arrays must have equal length and repeated digests must have the same diff ID.
- **`kill`** `signal` is an integer or a name (`"KILL"`, `"SIGTERM"`); default 15.
- **`remove`** on an id the agent no longer tracks (left on disk by an earlier boot) still deletes its directory; on a running container it fails with `container is running`.
- **`create` with `start`** behaves exactly as `create` followed by `start`: the result follows a successful exec and carries the same `pid`, and a tty start completes through the same deferred path. If the create part fails nothing is started. If the start part fails the container stays created, as it would after a separate `create`, and the error is the start error. An error from the start part of either `start` or `create` with `start` carries `"stage":"start"` next to `error` and `errno`; an error without it came from the create part. The host uses the combined call when the agent does not hold the container yet, or holds it with a different spec than the host last sent (for example a new IP at start), and when no `net_connect` has to run between the two. If the reply is lost (an error the agent did not report), for a container the agent did not hold before, the host sends best-effort `kill` 9 and `remove` before failing, because the agent may have started it. An agent that predates the flag ignores it and answers without `pid`; the host then sends `start`.
- **Mountpoint layer.** Every container overlay has `layers/.mountpoints` as its lowest layer, made once per boot with empty `etc/hostname`, `etc/hosts` and `etc/resolv.conf`. The agent binds the real files over those paths at start, so an image that lacks one no longer needs it created in the upper. Image content at those paths wins. `diff`, export and commit already skip the three files.
- **Network namespace.** `create` for a container with its own network namespace asks a helper thread to make one (loopback up, `ip_unprivileged_port_start` 0, open `ping_group_range`). `start` enters it only for the `clone3` call, so the container init is born inside it. At most one waits, each is used once, and a start that finds none makes its own with `CLONE_NEWNET`.
- **`create`** on an id whose directory survives from an earlier VM boot re-mounts the overlay over the existing upper (data kept).
- **`build_image`**: the host verifies the official arm64 BuildKit manifest by digest before supplying its layer list. The guest extracts exactly `size` context bytes (maximum 1 GiB, also enforced for compressed uploads and expanded tar files) under a private directory, then supervises the official BuildKit daemon and client in a private mount and PID namespace. The host keeps its write side open after sending the context so a disconnect can cancel the worker. Only exit code zero permits importing the Docker archive. Build cache is on the guest data disk.
- **Build bases.** The Mac resolves `FROM` images that only it can reach (local-only tags, tags that shadow a registry name, loopback registries, registries it holds credentials for), so credentials never reach the guest. Classic: the guest extracts `base_size` bytes to `/bases`, mounts it at `/noodle/bases` and passes `--oci-layout noodle=/noodle/bases` with `context:<familiar name>=oci-layout:noodle@<digest>` options (4 GiB maximum). Native: the adapter answers BuildKit's source-policy callback with CONVERT to `oci-layout://noodle.local/base@<digest>` and serves the blobs over the session content store `oci:noodle`, fetching them from noodled through `POST noodle/buildkit/base` and `GET noodle/buildkit/blob/{digest}`, both requiring the build capability header `X-Noodle-Build-Token`.
- **`buildkit_native`** opens the pinned worker's native BuildKit control connection. It takes the same verified provider layer list as `build_image`. The guest acquires the exclusive build-cache lease, starts the worker in a private PID and mount namespace, and waits for its private Unix socket before acknowledging. The host sends one activation byte (1) after consuming the acknowledgement. The rest of the stream is bidirectional HTTP/2. Disconnect kills the worker and releases the lease. There is no guest TCP listener. Docker clients use the host's authenticated local engine socket for `/grpc` and `/session`.
- **Build cache recovery.** Both worker entry points consume and durably remove a clean-cache marker under the same exclusive lease before starting BuildKit. A missing marker denotes an interrupted or older cache. The next build atomically detaches that cache beneath the private builder directory, removes it without following symlinks or crossing mounts, and starts empty. After an orderly worker exit, the supervisor flushes the filesystem before publishing a new marker. The actual daemon must acknowledge shutdown and exit normally on both entry points. The worker inherits the exclusive cache lock and a supervisor death signal. Interrupted builds can therefore require new downloads and uncached Dockerfile steps. Images and volumes use separate stores.
- **`unpack_layer`**: the first `{"ok":true}` frame is sent before the blob is read; the final result frame comes after the blob ends. `bytes` is the uncompressed tar size.
- **`archive_get`** answers the first frame as `{"ok":true,"name","size","mode","mtime"[, "link_target"]}` (the stat of the requested path, for `X-Docker-Container-Path-Stat`); a path ending in `/.` archives the directory contents only. Running containers are read through `/proc/<pid>/root`, so volumes and bind mounts are visible.
- **`archive_put`** extracts confined to the destination (`openat2` RESOLVE_IN_ROOT), no whiteout conversion. Entries become root-owned unless `copy_uid_gid` is true, matching `docker cp` and `docker cp -a`.
- **`exec`**: the first frame answer is sent after the process has actually exec'd, so "executable not found" arrives as `{"ok":false,"error":...}`. The host-visible end is `kind 3` exit and a control `exec_exit` event. The `env` entries override the container env by key.
- **TTY devices.** For `start` and `exec` with `tty`, the workload child opens the PTY from the container's own devpts instance after entering its root. The first PTY is `/dev/pts/0`; run binds that slave to `/dev/console`. The child transfers the master internally over a close-on-exec Unix socket with `SCM_RIGHTS`, and the agent acknowledges it after applying any pending resize, before the workload execs. Run receives the master and exec status through epoll; exec uses its separate stream worker. Attach workers, including those forked before start, receive their own duplicate from the agent. Output written before output registration stays in the PTY buffer. These internal messages do not change the host wire format or the rule that start/exec success follows successful exec.
- **`attach`**: output comes from the container log (the agent tails it), so it works before `start`. The agent writes the exit marker after draining output; attach and following logs watch the container directory for log and exit writes, then drain the final log before sending `kind 3`. Stdin on non-tty containers is a unix socketpair: `kind 4` shuts down the write side so the process sees EOF. For tty containers `kind 4` is ignored. An unwritable stdin or an unavailable tty master disables input forwarding but keeps the attach stream open to drain logs and deliver `kind 3`. Resize persistence is best effort once a live master is available; persistence failures do not end an attach stream.
- **`logs`**: `kind 3` exit frame (code 0) closes the stream. `follow` ends when the container has exited and the log is drained.
- **Exit codes**: `exit` event `code` is the exit status, or `128+signal`. An `oom` event precedes `exit` when the cgroup recorded an oom kill.
- **Networks.** `net_create` builds the bridge, an nftables table `noodle-<bridge>` (masquerade for ordinary networks; forward isolation for internal networks), and a DNS responder on `gateway:53` bound to that bridge. Internal network creation fails if isolation cannot be installed; forwarding between its bridge and other interfaces is dropped in both directions. A container on the default bridge uses `[gateway]` as its DNS server, and that responder only forwards: the host sends no records for the default bridge, so it has no container names. A container on a user network has `resolver` in its spec, `{servers[], links[] of {alias,target}}`: the agent opens a UDP socket at `127.0.0.11:53` inside the container's namespace, polled by the agent loop, closed when the container exits. It answers from the `dns_set` records of every network the container is attached to, after mapping a link `alias` to its `target`, so a link is visible only to the container that declared it. Names resolve from `dns_set` records plus `net_connect` `aliases` (each alias maps to the connected ip). Other names go to `servers`, in order, when the container has `--dns`; otherwise to the DHCP-provided resolver. A container only on internal networks gets SERVFAIL without forwarding. Forwarded replies must match the configured resolver address and port, randomized transaction ID, and original question. Each server gets 1.5 s; the agent's loop has a timer only while a forwarded query is outstanding. A bridge-mode container gets a veth pair named `v<id8><n>` on the bridge; the in-container name is `eth<n>` in connection order.
- **Seccomp.** The release runtime applies its own aarch64 syscall filter. It checks capabilities for operations such as mounting and namespace creation. Privileged and `seccomp=unconfined` requests are accepted only by the privileged containers VM (kernel command line `noodle.role=workload`), where no filter is installed; the main VM rejects them. In the main VM, container processes and the BuildKit worker inherit filters that reject `socket(AF_VSOCK)` and `io_uring_setup`. Both guest listeners accept only connections from the host CID.
- **Boot.** The agent first re-roots onto a tmpfs (an initramfs rootfs cannot be `pivot_root`ed, which containers need). Boot steps log as `noodle-init: ...` on `/dev/hvc0`; `noodle-init: ready` means both vsock ports are listening. DHCP tries four times (about 7 s worst case) and boot continues without a lease.

## Host assumptions (added by the engine; the agent must honour them)
- The agent keeps no state across boots. The host replays what it needs: `create` before every `start` and before any container-scoped op on a container the agent does not know (stopped containers after a wake). `create`, `net_create`, `volume_create` are idempotent and must reuse an existing `containers/<id>`, bridge or volume directory.
- `kill.signal` is a Linux signal number (integer). `exit` events may arrive before the `start` response; the host tolerates both orders.
- A spec `hosts` line whose address is the literal `host-gateway` (`host-gateway host.docker.internal`, or `host-gateway NAME` from `--add-host NAME:host-gateway`) names the Mac. The agent writes the router of its DHCP lease in place of `host-gateway`, and drops the line when boot continued without a lease. The result is an IPv4 line only: the VM's NAT link gives the Mac no IPv6 address a container can route to. Lines with any other address pass through unchanged, including IPv6.
- That address is the Mac's end of the vmnet NAT link (`bridge100`, usually `192.168.64.1`). UDP to it reaches Mac services bound to all interfaces or to that address. TCP to it goes through the Mac loopback relay (port 1034) when that is on, so it also reaches services bound only to `127.0.0.1` or `::1`; with the relay off, or from an internal network or the privileged containers VM, TCP behaves like UDP.
- An archive deeper than 100 directory levels fails with ENAMETOOLONG instead of dropping the deeper entries. `export`, `archive_get` and `layer_get` carry no trailer: the host streams them to the client, and a failed one ends without the tar end-of-archive blocks.
- `commit` with an unchanged upper dir should send an empty tar (<= 1024 bytes); the host then adds no layer.
- `unpack_layer.diff_id` must match the expected image config diff ID for every media type, including plain tar.
- Host-side removals for containers/volumes/layers while the VM sleeps are queued and replayed (`remove`, `volume_remove`, `layer_remove`) at the next boot. The guest detaches a removed volume into private trash before deleting its contents. A reused volume name cannot mount until the host persists the successful removal acknowledgement.

## DNS through the Mac
The VM's resolver sits behind vmnet and can stop answering while the Mac's own resolver works, for example after a network change. A forwarded query with no `--dns` servers goes to the VM's resolver first. If that resolver returns SERVFAIL or REFUSED, or says nothing for 800 ms, the agent sends a `dns_query` event and waits up to 3 s for `dns_answer`, then returns SERVFAIL. The daemon answers from the Mac's system resolver on its own queue, so VPN and split DNS apply. Nothing runs on this path until a query needs it. Queries for `--dns` servers never take it: those servers are what the user asked for.
